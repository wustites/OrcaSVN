# Windows 无 USN 权限时的状态检查

本记录汇总 2026-11-02 本轮对话中的问题定位、源码修改、实测、模拟与结论修正。OrcaSVN 源码位于 `D:/project/OrcaSVN`，测试工作副本为 `D:/project/Go1.3`。用户要求本机无 Rust 环境且无需安装；本轮未安装 Rust，未编译或替换桌面程序。本地验证阶段先保留未提交改动，后经用户确认提交说明，按草稿 PR 交付。

本轮对 Go1.3 的操作为只读状态查询、缓存/元数据检查和监听探针，没有修改其业务文件，也没有解密或替换 TSD 文件。修改、重命名、删除等通知测试使用独立临时目录；重开模拟使用独立临时快照，不覆盖应用缓存。

## 结论与适用范围

- 完整 `svn status --xml` 本身就需要约 10.6–13.0 秒；原打开流程还会在它之前自行遍历文件清单，形成额外等待。
- 原生缓存已存在、格式匹配且未过期，但没有 USN 索引。缓存可以减少 SVN 查询范围；无 USN 时，重开仍需核对关闭期间的文件变化。
- 文件元数据差异只产生待核对候选，最终状态由 SVN 判定。单纯 TSD 文件大小视图差异不会由 OrcaSVN 直接标成已修改；本轮也没有证据将 TSD 列为主要性能瓶颈。
- 当前执行权限打开 USN 所需卷句柄返回错误 5。它与缺少 USN 索引的现象一致，但应用当时未记录初始化错误，不能完全追溯原进程的失败原因。
- 本轮加入普通权限可用的目录通知回退，主要减少同一进程中后续刷新的遍历成本；它不会为已关闭的应用保存离线变更历史。
- 匹配磁盘快照、无额外修改时，第二次打开的 Python 模拟中位数约 4.43 秒，清单遍历仍约 3.88 秒。不是 Rust 或桌面端实测，不能用它宣称新版应用已达到该速度。
- 本轮已通过 58 项前端单测、前端构建及 Windows API 探针。Rust 编译、原生回归测试、打包和桌面打开耗时均待验证；现有桌面程序不会因源码修改自动生效。

## 原因与测量

2026-11-02 在本机只读测试 `D:/project/Go1.3`，SVN CLI 版本为 1.14.5。完整 `svn status --xml` 用时约 10.6–13.0 秒，返回 5 个修改和 90 个未版本化条目，XML 输出约 15.5 千字符。以下均为本地工作副本检查，不是下载远端仓库或检索提交历史的耗时。

| 检查项 | 本轮观测 | 说明 |
| --- | --- | --- |
| 完整 `svn status --xml` | 首轮 12.979 秒，复测 10.864、10.629 秒 | 95 条状态不代表只检查 95 个文件 |
| 加 `--ignore-externals` | 10.660 秒 | 本次慢点未因关闭 externals 扫描而消失 |
| 加 `-q` 的 XML 状态查询 | 11.010 秒 | 本次未显示明显耗时改善 |
| `svn info --xml` | 约 0.20 秒 | 本地仓库元信息查询 |
| `svn info --show-item revision --no-newline` | 约 0.23 秒 | 本地版本号查询 |
| 当前权限打开 D 盘卷句柄，访问权 `GENERIC_READ` | 错误 5：拒绝访问 | USN 启用条件探针，不是应用原进程日志 |

工作区清单包含 95,356 个文件和 15,071 个子目录，合计 110,427 项；把工作区根目录也计入目录统计时，共 15,072 个目录。清单不深入 `.svn/pristine`、`.svn/tmp`，但会进入普通未版本化和被忽略的目录。原生磁盘快照约 13.7 MiB、版本 6、未过期，但没有 USN 索引。

原先 USN 初始化错误被 `.ok()` 隐藏，普通回退路径在 Windows 上每次重新枚举工作区。只读查询 `wc.db` 并比较当前文件元数据后，95,257 个正常受版本控制文件中有 93,622 个匹配 SVN 大小/时间缓存，1,624 个大小相同但时间不匹配，4 个大小不匹配，7 个缺少缓存字段。后面三类共 1,635 个候选，不能全部直接通过原缓存跳过核对；其中时间不匹配文件合计约 100 MB。没有跟踪实际内容读取量，不能断言每次都读取全部 100 MB，也不能把 1,635 个候选说成 1,635 个实际修改。以上都是本轮观测，不是修改后桌面启动基准。

### TSD 元数据候选仍由 SVN 排除

“文件大小或时间与缓存不同”只说明需要再核对，不能直接转换为“已修改”。当前 [operations.rs](../src-tauri/src/svn/operations.rs) 的完整和定向查询都取自 SVN XML 结果：普通 `normal` / `none` 状态被过滤，定向查询还过滤 `ignored`；如果文件属性确实为 `modified` / `conflicted`，则仍保留。定向结果合并时会先移除被核对路径的旧状态，再加入 SVN 返回的有效状态，所以 SVN 判定已恢复干净的文件不会保留旧的“已修改”标记。

因此，TSD 仅造成文件大小视图不同、但 SVN 判定没有内容或属性修改时，会在最终状态中排除，无需为 TSD 文件另设忽略规则。本轮完整 SVN 查询实际返回的仍是 5 个修改和 90 个未版本化条目，不能把模拟器产生的 955 个大小差异当成 955 个 SVN 修改。这里确认的是现有源码的判定与过滤方式，并非新增 Rust 实现已通过运行测试。

跨进程比较不一致可能增加模拟器中的候选或触发完整查询，这是模拟方法的限制；本轮没有量化 TSD 在真实 OrcaSVN 进程中的额外耗时。性能结论继续聚焦已测得的完整 SVN 查询和文件清单遍历，不把 TSD 本身定为主要原因。

## 缓存为何没有免掉扫描

需要区分不同用途的缓存：

| 缓存 | 保存内容与用途 | 本轮核实结果或限制 |
| --- | --- | --- |
| 前端展示快照 | 小型状态列表及仓库信息，提前显示上次结果 | 源码限制为最多 5 个工作区、24 小时、每份不超过 1,000 条状态，存储文本总量不超过约 1 Mi 字符；未读取实际 WebView 存储，不能断言本轮一定命中 |
| 原生内存缓存 | 当前进程中的状态和文件清单 | 最多 3 个工作区；退出进程后不能单靠它恢复可信状态 |
| 原生磁盘快照 | 成对保存文件清单和原始 SVN 状态，用来核验和缩小查询范围 | 最多 5 个工作区、24 小时、单份 64 MiB、清单 500,000 项；Go1.3 实际快照约 13.7 MiB，没有 USN 索引 |
| SVN 自身的文件信息缓存 | `wc.db` 内的大小、修改时间等信息，辅助 SVN 判断文件状态 | 与 OrcaSVN 快照不同；本轮发现部分记录不能直接匹配当前元数据 |

原无 USN 路径是“读取快照 → 遍历当前工作区 → 比较差异 → 复用状态或执行 SVN”。因此缓存命中且无变化时可以省去完整 SVN 查询，但还没有省去遍历。目录结构、SVN 管理数据、配置发生变化，或达到强制/周期核对条件时，仍会完整检查。Unix 的目录子项索引复用没有在 Windows 元数据回退路径启用。

前端展示快照解决的是先显示上次结果的问题，不代表后台核验已经完成。页面可能已有内容，但仍显示检查中。相关实现见 [workspaceSnapshot.ts](../src/utils/workspaceSnapshot.ts) 和 [useWorkspace.ts](../src/composables/useWorkspace.ts)。

## 文件清单遍历具体做什么

清单不是 SVN 变更列表，也不是每次读取全部文件正文。其主要步骤为：

1. 递归列出每个目录中的直接子项，记录相对路径和类型，按规则跳过 SVN pristine/tmp，不跟随符号链接。
2. 读取目录自身元数据；读取普通文件的大小、修改时间，符号链接还记录目标，Unix 另记录 ctime。
3. 对路径排序，建立父目录到直接子项的索引，供差异比较和快照校验使用。
4. 与旧清单比较新增、删除、类型或元数据变化。没有变化就复用状态；少量普通文件变化交给定向 SVN 查询；范围不可靠则完整核对。

Go1.3 的 95 条状态来自约 11 万个清单项，扫描成本取决于被检查的文件和目录数量，而不是最终显示的变更条数。先前 .NET/Python 简化遍历约 2.5–3.0 秒，只能作为参考；完整重开模拟还计入目录自身元数据读取、排序、子项索引等，清单阶段约 3.88 秒，不能混用两种计时口径。

## 修改后的行为

- USN 可用时继续使用原有持久化增量索引；初始化失败记录原因，不请求提权。
- 无 USN 索引时，以 `FILE_LIST_DIRECTORY` 和 `ReadDirectoryChangesW` 对工作区根目录建立一条递归、异步通知请求。无需读取卷句柄，也不逐目录注册监听。最多保留三个内存工作区，淘汰时释放监听。
- 通知请求由每个监听独占的专用线程发起和轮询。Windows 会在发起线程退出时取消其未完成的 I/O，因此不能使用 Tokio 阻塞线程池中会空闲退出的线程。
- 目录通知只用于本地固定磁盘。网络卷、可移动卷和无法识别盘符的路径可能漏报或延迟通知，继续在每次刷新时比较文件元数据。
- 首次建立可信状态后，无通知直接复用结果；普通文件的修改、创建、删除和重命名候选交给现有定向 SVN 查询。每次核对工作区根目录身份、SVN 配置及选定子目录之外的祖先管理数据。
- 目录结构或 SVN 管理数据变化、通知溢出、候选超过 256 个、路径解析异常、根目录被替换或查询失败时，重新建立监听并完整检查。保留手动刷新和每五分钟完整检查。
- 首次无缓存、手动刷新及周期全查时，若已建立通知请求，文件清单与 SVN 查询并行。两者完成后检查通知；期间有变化、通知不可靠，或清单中有条目在查询窗口内被修改（通知可能尚未到达），就放弃这份清单和快照，下次按先清单、后 SVN 的顺序重新建立基线。没有可用监听时保留先清单、后 SVN 的顺序。
- 原生快照写入继续串行执行，但等待上一轮写入移到后台。目录通知更新的状态不与旧文件清单组成新的磁盘快照，避免重开时误判。完整检查和离线核验仍可生成经过前后校验的快照。

目录通知只在当前应用进程存活期间有效。关闭后重开，没有 USN 时仍需文件元数据比较，不能承诺完全免扫描。通过工作区之外的硬链接写入可能不产生工作区内通知，需依赖手动或周期完整检查，因此此类修改最多可能滞后五分钟；需要这种覆盖时保留 USN 路径。

| 场景 | 当前源码策略 | 本轮验证边界 |
| --- | --- | --- |
| 没有可信缓存首次打开 | 建立监听；条件满足时清单与完整 SVN 查询并行，期间有变化就放弃清单 | 已改源码，未测 Rust 端首次打开耗时 |
| 关闭后重开，有匹配快照但无 USN | 先核验离线文件清单，再决定复用/定向/完整查询 | Python 磁盘模拟约 4.43 秒 |
| 同一进程中，监听已就绪且无变化 | 检查通知、环境与根目录身份后复用状态 | 系统通知探针可用；Rust 路径未运行 |
| 同一进程中少量普通文件变化 | 通知选出候选，交给已有定向 SVN 查询并合并状态 | 已补 Rust 回归用例，未执行 |
| 通知溢出、结构/管理数据变化、手动或周期核对 | 放弃不可靠范围，完整检查 | 已保留回退及相关用例，尚待原生验证 |

## 为什么不能只检查父目录修改时间

目录修改时间不是整棵子树的“最后变化时间”。本机 D 盘临时目录实测：建立 `测试根/sub/a.txt`，在每项操作前后分别读取 `sub` 和测试根的修改时间，写入时关闭文件句柄。结果如下；测试没有修改 Go1.3 内容，临时文件与目录已清理。

| 对 `sub` 内文件的操作 | 直接父目录 `sub` 的修改时间 | 上一级测试根的修改时间 |
| --- | --- | --- |
| 原地修改已有文件内容 | 不变 | 不变 |
| 新建文件 | 改变 | 不变 |
| 重命名文件 | 改变 | 不变 |
| 删除文件 | 改变 | 不变 |

这些结果说明，目录项的增删和改名可以改变直接父目录的修改时间，但变化不会自动逐层传到所有祖先目录。原地修改文件内容也不一定改变直接父目录时间。例如编辑 `Go1.3/src/eagle5/a.go`，不能通过 `eagle5`、`src` 或 `Go1.3` 的目录修改时间判断内容是否变化。部分编辑器采用临时文件替换保存，可能顺带改变目录时间，但不能把这种保存方式当作所有修改的前提。

目录时间可以辅助判断是否需要重新列举直接子项。当前 Unix 目录索引复用还核对 ctime、设备号、inode 和时间稳定性；即使复用目录索引，也仍检查文件自身的元数据。Windows 普通回退路径则利用目录枚举返回的文件元数据。两者都不能因为父目录时间没变，就跳过整棵子树的文件检查。

递归目录通知通过系统事件报告子树变化，USN 通过卷日志记录变化，都不是读取父目录修改时间。应用关闭后，目录通知不会替应用积累离线历史；没有可用 USN 时，重开仍需文件清单核验。这也是匹配快照的第二次打开模拟仍耗时约 4.43 秒、其中清单约 3.88 秒的原因。

时间戳本身也可能被显式设置，更新时间受句柄关闭等条件影响，不能把时间相同当作内容绝对相同的证明。接口说明见 [Windows 文件时间](https://learn.microsoft.com/en-us/windows/win32/sysinfo/file-times)和 [ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)。

## 第二次打开模拟（2026-11-02）

本机无 Rust，使用标准库 Python 脚本 [benchmark-workspace-reopen.py](../scripts/benchmark-workspace-reopen.py) 复现无 USN 时的重开流程。每轮从新的内存状态开始，建立真实 Windows 目录通知，并行查询本地版本号，读取/解析/校验磁盘快照，枚举目录及文件元数据，构建排序清单和子项索引，比较差异，必要时调用真实 SVN。文件系统缓存已预热；不包含 Python 进程创建、桌面程序启动、Tauri IPC、WebView、Vue 渲染或后台快照写入，也不等于 Rust 实现计时。

为了测量“刚生成缓存、没有额外修改就重开”，先单独准备与当前文件视图一致的快照：采集清单、查询完整 SVN 状态、再次采集并确认两份清单相同，再写入独立临时磁盘文件。准备过程不计入重开时间。每轮重读该临时文件，结束后删除它；不覆盖应用缓存或工作副本。

| 轮次 | 总耗时 ms | 快照读取/解析/校验 ms | 当前清单 ms | 差异比较 ms | SVN 状态查询 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 4,423.6 | 379.2 | 3,858.8 | 153.6 | 0 |
| 2 | 4,425.5 | 364.8 | 3,881.7 | 153.0 | 0 |
| 3 | 4,434.6 | 363.7 | 3,898.1 | 144.7 | 0 |

总耗时中位数 **4,425.5 ms（约 4.43 秒）**。三轮均无候选变化，复用已有 SVN 状态；仍需枚举 110,427 个清单项、15,072 个目录。目录自身的单独元数据读取约占清单耗时中的 1.52 秒。版本号查询并行完成，监听/进程启动等准备约 25–31 ms。原始结果见 [磁盘快照重开模拟 JSON](benchmarks/go1.3-reopen-fresh-disk-simulation-2026-11-02.json)。

这次模拟用于分解重开仍需支付的检查成本，没有在同一环境运行修改前后的 Rust 程序做对照。原代码在匹配快照、无变化时也可以复用 SVN 状态，因此不能仅凭“完整 SVN 约 11 秒、匹配快照模拟约 4.43 秒”，就认定本轮源码修改让第二次打开从 11 秒降到了 4.43 秒。

另有探索性测量：直接将原应用快照与 Python 看到的元数据比较，三轮均出现 955 个大小候选，触发模拟器中的完整 SVN 状态查询，中位数 15.11 秒。后续核查发现这些候选全部只有大小不同、时间戳相同；其中 `.svn/wc.db` 在 Python 视图中少 4,096 字节，通过 Git Bash 读取磁盘头可见 TSD 标记。这提示跨进程文件视图口径存在差异，**不能据此认定原生 Rust 缓存失效、文件确实被修改，或 TSD 是主要耗时原因**。是否修改仍以 SVN 结果为准，正常项会被排除。该探索性数据及限制见 [原应用快照跨进程比较 JSON](benchmarks/go1.3-reopen-simulation-2026-11-02.json)；其中最早的匹配基线测量从内存载入快照，正式磁盘重开模拟使用上表数据。

重跑匹配快照的磁盘模拟（准备阶段会额外执行一次只读完整 SVN 状态查询）：

```powershell
py -3 -u scripts/benchmark-workspace-reopen.py --workspace D:/project/Go1.3 --snapshot "$env:LOCALAPPDATA/com.orcasvn.desktop/workspace-status/status-7ddb0d87c9824ad3.json" --scenario fresh --runs 3 --output docs/benchmarks/go1.3-reopen-fresh-disk-simulation-2026-11-02.json
```

脚本只需 Python 和现有 SVN CLI，不依赖 Rust；`--scenario existing` 可测已有应用快照的跨进程比较，`--scenario both` 依次测两种情况。已有快照的路径和有效期需要以执行时状态为准，不能把损坏、过期或不同文件视图的结果当成匹配缓存场景。结果文件由 `--output` 明确指定，重复使用同一路径会覆盖该结果文件；不会覆盖输入的应用快照。

## 与单独 svn status 的交替比较

同日在 Go1.3 上另做三轮交替测量：完整 `svn status --xml` 与匹配磁盘快照的 Python 重开模拟先后交替运行，文件系统缓存已预热。每轮校验完整 SVN 状态与准备快照时相同，缓存模拟均无候选变化、直接复用状态。基线包含 SVN 子进程和输出接收；模拟还包含目录通知准备、并行本地版本号查询、磁盘快照读取/校验、当前清单与差异比较，不包含桌面启动和渲染。

| 轮次 | 完整 SVN ms | 缓存重开模拟 ms | 耗时减少 |
| --- | ---: | ---: | ---: |
| 1，先 SVN 后缓存 | 10,782.8 | 5,098.9 | 52.7% |
| 2，先缓存后 SVN | 10,291.2 | 4,702.5 | 54.3% |
| 3，先 SVN 后缓存 | 10,335.7 | 4,480.8 | 56.6% |
| 各自中位数 | 10,335.7 | 4,702.5 | 54.5% |

按各自中位数计算，匹配缓存模拟少等待约 5.63 秒，耗时约为完整 SVN 的 45.5%，速度比约 2.20 倍。说明“无变化时复用 SVN 状态”相对每次运行完整 SVN 有明显收益，剩余主要成本仍是清单遍历。本批模拟中位数约 4.70 秒，与前一批约 4.43 秒存在环境波动；两批均保留，不用最低值代替中位数。原应用快照在本次测试期间未被测试脚本覆盖，实际校验其内容也未变化。

这不是修改前后 Rust 程序的对照。原代码在匹配缓存时也能省去 SVN 查询；本轮结果不能单独证明新增通知回退让桌面程序快了 54.5%。实际原生接口和桌面效果仍待已有 Rust 环境编译后测量。原始结果见 [SVN 与缓存模拟交替比较 JSON](benchmarks/go1.3-status-vs-cache-simulation-2026-11-02.json)。
